## 2026-10-25 — DOC-4: every docs build prints a MkDocs 2 banner

- **Context:** every `mkdocs build --strict` in M2.
- **Problem:** a "Zensical is its maintained successor" banner adds noise to the hook and CI logs.
  It also signals that a future MkDocs 2 may change the strict-build behaviour the docs gate
  relies on.
- **Proposal:** set `NO_MKDOCS_2_WARNING=1` in the hook and in CI. Pin `mkdocs<2` with a note, or
  plan the migration in the template.
- **Status:** open

## 2026-10-25 — SEC-14: `private/` is invisible to cloud sessions

- **Context:** the user moves between local and cloud agent sessions, and wanted a session handoff
  in `private/`.
- **Problem:** `private/` is git-ignored by design, so a session cloned from GitHub has neither the
  handoff nor the local-only test data. Nothing in the standards says so.
- **Proposal:**
  - State in SEC-14 that `private/` is local-only.
  - Suggest a layout that keeps personal data apart from the rest (`private/handoff/`,
    `private/tools/`), so the rest can be uploaded on its own; handoffs carry a time stamp.
  - Recommend a committed, dated handoff without personal data when cloud continuity matters.
- **Status:** open

## 2026-10-25 — missing rule: a standard fail-fast merge procedure

- **Context:** every PR here followed the same sequence:
  1. push;
  2. `gh pr create`;
  3. wait for the checks, and refuse on any failed or pending one;
  4. squash-merge;
  5. return to `main`;
  6. watch main's CI and the release.

  Early mistakes led to a helper script: deleting a branch after a failed push, and a failing
  `grep -v` stopping a command chain.
- **Problem:** the standards define the gates but not the merge procedure. Every project and every
  agent session re-invents it, and a cloud session does not have the local helper.
- **Proposal:** add `standards ship --title ... --body-file ...` to the CLI, with fail-fast
  semantics. Document it in `09-ci-cd.md` and the PR template.
- **Status:** open

## 2026-10-25 — PY-1 / ruff RUF001-003: typographic characters in docstrings

- **Context:** French and unit text in docstrings (`×`, `–`, `≤`, `€`).
- **Problem:** RUF002 flags `×` and the en dash, which pushes towards ASCII rewording of correct
  typography.
- **Proposal:** set `allowed-confusables = ["×", "–", "≤", "€"]` in the template's ruff
  configuration, as a list the project can override. Or document the choice: ASCII in code,
  typography in Markdown.
- **Status:** open

## 2026-10-25 — DOC-12 / TST-14: notebooks have no readable committed source

- **Context:** notebooks are generated by nbformat scripts kept outside the repository, then
  committed already run (M2 notebooks 04 and 05).
- **Problem:** only the `.ipynb` JSON is committed, so diffs are unreadable. Changing a cell means
  editing JSON or keeping a private generator script; notebook 04 was regenerated three times this
  session.
- **Proposal:** pair each notebook with a jupytext percent-format source
  (`notebooks/NN-concept.py`). Add a hook that checks the `.ipynb` matches its source and is
  executed. Review happens on the `.py`.
- **Status:** open

## 2026-10-25 — VER-5: the wheel's package data is never tested

- **Context:** M2 ships data inside the package (`adapters/packs/data/**.toml`), loaded with
  `importlib.resources`.
- **Problem:** tests run against `src/`, so a build configuration that dropped non-Python files
  would pass every gate and release a broken wheel. The wheel was checked by hand (`uv build`,
  `unzip -l`).
- **Proposal:** add a CI job that builds the wheel, installs it in a clean venv and runs a smoke
  test: import, entry points, `importlib.resources` lookups. Optionally, check the expected data
  globs in the wheel.
- **Status:** open

## 2026-10-25 — COM-2: nothing detects an unmarked breaking API change

- **Context:** M2 task 2b removed public classes released in v0.8.0. The commit was first written
  without `!` and `BREAKING CHANGE:`; this was noticed by hand before pushing.
- **Problem:** COM-2 checks the format of a breaking commit, not whether a change is breaking. A
  removed or renamed public name can ship as a minor `feat`.
- **Proposal:** add `standards check-api`, using griffe to diff the public API against the last
  tag. Removed names or incompatible signatures then require `!` and a `BREAKING CHANGE:` footer.
  Run it in the pre-push stage and in CI.
- **Status:** open

## 2026-10-25 — TST-12: two test files with the same name silently drop tests

- **Context:** M1 added `tests/golden/test_profiles.py` next to `tests/unit/domain/test_profiles.py`.
- **Problem:** pytest's default import mode cannot load two test modules with the same basename;
  under mutmut the whole module failed to collect, so its tests never ran against any mutant and
  the score fell from 96 % to 86 % with no error in the gate.
- **Proposal:** use `--import-mode=importlib` in the template's pytest configuration, and/or a
  check that refuses duplicate test basenames; make `mutmut` fail the gate when test collection
  fails.
- **Recurrence:** during M2 task 2b, `tests/unit/adapters/test_schedule_files.py` and
  `tests/security/test_schedule_files.py` collided. This time plain pytest failed at collection,
  so the problem was caught, but only after the fact.
- **Status:** open (the files were renamed here)

## 2026-10-25 — LAY-7: `copier update` leaves conflict markers in `uv.lock`

- **Context:** updating to v0.4.2.
- **Problem:** the post-render task `uv lock` also runs during updates, so both template renders
  carry a lockfile and their diff conflicts with the project's; the `check-toml` and `uv-lock`
  hooks caught the broken file before it was committed.
- **Proposal:** run `uv lock` only on `copier copy`; after an update, the `uv-lock` hook tells the
  developer to re-lock, which is one command.
- **Status:** filed https://github.com/wghami/python-project-standards/issues/18, resolved in v0.4.3
  (tasks run on the first render only; this one update from v0.4.2 needed `uv.lock` restored)

## 2026-10-25 — DOC-3: the generated API reference only showed the package docstring

- **Context:** the user noticed that the published reference page was empty after M1 added modules.
- **Problem:** mkdocstrings rendered `::: myenergy` without `show_submodules`; the strict build
  passed, so no gate noticed.
- **Proposal:** show submodules, and make the template's smoke job check that a submodule's
  function appears in the built reference.
- **Status:** filed https://github.com/wghami/python-project-standards/issues/16, resolved in v0.4.2

## 2026-10-25 — missing rule: a git-ignored place for personal data

- **Context:** the user provided a real electricity bill as a test reference; it must never reach
  GitHub.
- **Problem:** the template has no convention for personal or confidential inputs; each project
  would improvise, and a slip publishes personal data.
- **Proposal:** the template's `.gitignore` ignores `private/`; a rule (e.g. SEC-14) says personal
  data lives only there; tests that need it are skipped when it is absent, and CI uses synthetic
  equivalents with the same structure.
- **Status:** filed https://github.com/wghami/python-project-standards/issues/14 (with the
  mkdocs-jupyter `.cache/` folder), resolved in v0.4.1 as SEC-14

## 2026-10-25 — COM-4: a breaking PR title can never pass `check-pr-title`

- **Context:** the PR renaming the project, titled `build(release)!: …`.
- **Problem:** the title was held to COM-2's footer rule, but a title has no body; the footer
  reaches `main` through the squash body (BR-4) and is already checked on each commit.
- **Proposal:** check PR titles as headers only.
- **Status:** filed https://github.com/wghami/python-project-standards/issues/11, resolved in v0.3.4

## 2026-10-25 — DOC-4, TST-11, TST-12, CI-7: five gate holes found rolling out v0.3.1

- **Context:** first main-branch run after updating to v0.3.2; the docs job, the release job and
  the nightly job failed, while the local hooks had passed.
- **Problem:** (1) `mkdocs build --strict --quiet` lets warnings through, so the local docs gate
  was blind; (2) project pages had to be listed in the template-owned `mkdocs.yml` nav, which the
  update replaced; (3) zero mutants (no functions yet) failed the nightly job like a crash;
  (4) the perf job hit a pytest usage error; (5) an open release blocker turned `main` red on a
  push that released nothing.
- **Proposal:** fix all five upstream, each with a test or smoke check.
- **Status:** filed https://github.com/wghami/python-project-standards/issues/9, resolved in v0.3.3

## 2026-10-25 — DOC-10: the README task aborts `copier update` on existing projects

- **Context:** updating this project from v0.2.x to v0.3.1.
- **Problem:** the new post-render task `standards readme --write` fails when README.md has no
  marker blocks yet, which is the case for every project rendered before DOC-10. The README is
  project-owned, so the update cannot add the markers itself.
- **Proposal:** the task should not fail the update. It should tell the user to add the markers,
  and the `readme` hook keeps enforcing DOC-10 on the next push.
- **Status:** filed https://github.com/wghami/python-project-standards/issues/7, resolved in v0.3.2
